# Synthetic community-policy API adapter

**Status:** experimental reference adapter for discussion and local testing only.

This directory wraps the dependency-free policy evaluator in a small Django REST Framework view. It is deliberately separate from Aidora's application and does not add routes, models, migrations, or settings to the Aidora backend.

## Run locally

Use Python 3.12+ in a disposable virtual environment:

```bash
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
python -m unittest -v
```

The test suite uses DRF's request factory and an authenticated synthetic test principal. It covers server-side policy resolution, known/unknown/duplicate approval references, attempts to submit a caller-controlled policy, denied purposes, expiry, and malformed inputs.

## API contract

`POST /synthetic-policy/evaluate/` (the path is illustrative; this prototype does not register a URL route).

Request JSON:

- `purpose`, `action`, `context`: synthetic request attributes
- `approval_references`: Ed25519-signed evidence tokens resolved using an explicitly configured issuer public-key registry

The evaluation timestamp is generated by the server; clients cannot provide it. Before an `ALLOW` is returned, references are consumed in a local SQLite database configured through `AIDORA_APPROVAL_STORE_DB`. The setting must point to a durable local file. If it is missing, the endpoint fails closed with `REVIEW`.

The adapter does **not** accept a caller-supplied policy. It resolves a fixed synthetic policy inside the server-side module and verifies each approval token against an operator-configured Ed25519 public-key registry. This is a demonstration of a trust-boundary shape only; the policy remains a hard-coded synthetic fixture, and the configured issuer/key mapping is only as trustworthy as the process configuration and secret handling.

A successful evaluation returns HTTP 200 with `decision` (`ALLOW`, `DENY`, or `REVIEW`), policy identifiers, and reason codes. Invalid request structure returns HTTP 400. The view requires authentication through DRF's `IsAuthenticated` permission; a real deployment would also need an explicitly designed identity, authorization, audit, and operational security model.

## Scope and safety limits

- This is not connected to Aidora's production backend, SRHIN, or any external service.
- It uses synthetic examples only. Never submit real health, participant, refugee, or other sensitive data.
- The endpoint is not mounted or deployable as-is; no URL configuration or production settings are supplied.
- Approval tokens use Ed25519 signatures over canonical JSON claims. The API verifier receives public keys only; the private signing key belongs in a separately controlled issuer process and must never be configured in the API. Claims bind approval ID, issuer ID, subject, policy ID/version, purpose, action, context, status, issue time, and expiry. Unknown keys, invalid signatures, scope mismatches, noncanonical payloads, and expired/future evidence fail closed.
- SQLite provides transactional one-time-use enforcement for processes sharing the same local database file. It is not a distributed multi-host store, and network filesystems or database-file loss are outside this prototype's guarantees. Backups, access controls, retention, key management, and recovery are not implemented.
- The keyring is configured with `AIDORA_APPROVAL_ED25519_PUBLIC_KEYS` (JSON mapping key IDs to issuer IDs and base64-encoded 32-byte Ed25519 public keys). Keep private signing keys outside the API and source control. During rotation, add the new public key before the issuer begins signing with its matching private key; retain old public keys only while corresponding tokens may remain valid, then remove them. The prototype does not provide a secret manager, secure key generation, access controls, or key ceremony.
- The underlying core evaluator remains a pure function that trusts its policy and normalized approval inputs; direct callers must not treat it as a security boundary.
- An `ALLOW` result is not legal, ethical, contractual, or community approval and does not itself enforce access restrictions.
- Do not use it to protect real data. Any host-specific implementation must first be co-designed and validated with the host and affected communities, and must reuse existing governance tools where appropriate.

The core evaluator and its limitations are documented in `../community-policy-check/README.md`.

## Synthetic audit-log experiment

`audit_log.py` provides a small in-memory hash-chained event log for demonstrations. It records only the decision, policy identifier/version, reason codes, timestamp, sequence, previous hash, and event hash. It deliberately does not record request context, approval references, participant information, or raw data.

Run its tests with:

```bash
python -m unittest -v test_audit_log.py
```

The adversarial tests cover event modification, middle-event deletion, reordering, previous-hash changes, event-hash changes, and malformed input. They also demonstrate an important limitation: deleting the final event leaves a valid shorter prefix. Detecting tail truncation requires an independently protected checkpoint or external anchoring of the latest chain hash.

This implementation is an integrity demonstration only. The list is mutable in memory, hashes are not signatures, and there is no durable or independently protected storage. It is not an immutable audit system and must not be used for real or sensitive data.


## Replay protection experiment

The API now requires `AIDORA_APPROVAL_STORE_DB` to point to a durable local SQLite file. Approval references are consumed in one transaction using an immediate write lock and a unique primary key. A batch is all-or-nothing, and a missing store fails closed with `REVIEW`. This improves the prototype over process-local replay state for processes sharing the same local database file.

This is still not production-grade consent infrastructure. It does not solve distributed multi-host coordination, authenticated approval issuance, distributed storage, backup/recovery, or policy-store integrity. Do not use a shared network filesystem as a substitute for a purpose-built transactional service. The fake approval fixture remains hard-coded and publicly inspectable.


## Signed approval evidence and revocation experiment

The API no longer accepts the hard-coded public approval fixture. Each value in
`approval_references` must be an Ed25519-signed token. The issuer-side helper is
`approval_evidence.sign_approval_evidence`; it accepts an Ed25519 private-key
object and is intended for a separately controlled issuer process, not an HTTP
issuance endpoint. The API only verifies tokens and never issues approvals.

Configure the verifier with:

- `AIDORA_APPROVAL_ED25519_PUBLIC_KEYS`: JSON object keyed by key ID. Each
  entry contains `issuer_id` and `public_key`, where `public_key` is a
  base64-encoded 32-byte Ed25519 public key. The verifier accepts any
  configured key ID, allowing a planned rotation overlap. No private key or
  active signing-key setting belongs in the API process.

The token binds issuer, approval ID, subject, policy ID and version, purpose,
action, context, status, issue time, and expiry. Tokens with a lifetime longer
than 90 days are rejected. Keep old verification keys only while tokens signed
with them may still be valid, then remove them. Ed25519 separates signing from verification: possession of the configured
public key does not allow the API to mint approval tokens. Protect the issuer's
private key in a separate process or managed signing service.

Revocation markers are persisted in the same SQLite database through
`SQLiteApprovalStore.revoke(...)`. The API checks revocation before evaluation,
and the atomic consume transaction checks again to close the check/consume race.
The prototype exposes no public revocation endpoint: revocation must be invoked
by a separately authorized administrative process. A real system needs a
defined issuer governance process and authenticated, audited revocation
authority.

This remains synthetic reference code, not a trusted community approval
service. The configured issuer identity is an operator assertion, not proof of
community mandate. There is no production identity proofing, secret manager,
distributed database, externally anchored audit trail, secure key ceremony,
or independent authorization authority. Do not use it with real data or treat
a signed token as evidence of actual community consent.
